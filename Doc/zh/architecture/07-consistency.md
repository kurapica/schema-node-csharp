# TODO：整体语义一致性分析（Semantic Consistency Analysis）

## 1. 目标

探索 SchemaNode Runtime 对整个语义空间进行持续一致性分析的能力。

SchemaNode 不仅负责语义定义、编译和执行，还应能够理解不同语义对象之间的依赖与影响，判断它们组合后是否仍然符合已经声明的整体业务意图。

核心目标：

**从局部语义合法性，扩展到整体业务意图的一致性判定。**

这不是传统意义上的函数正确性证明，也不是形式化验证系统，而是基于结构化语义和函数意图，对整个系统进行持续的影响分析与冲突检测。

## 2. 基本思路

### 2.1 基于语义函数进行分析

语义函数不仅是可执行单元，也是可解释、可转换、可分析的意图载体。

函数可能表达：

- 数据读取与引用
- 数据修改与保存
- 数据汇总与派生
- 数据推送与事件触发
- 函数调用与依赖
- 工作流中的状态变化

这些操作虽然可以组合成复杂业务，但其意图仍然可以通过函数展开和分析获得。

现有 Multi-target Compile 和 QueryFilterCompileContext 已经具备部分基础能力。

可以进一步探索增加面向一致性分析的推导目标，从函数意图中提取统一的影响描述。

### 2.2 开放式分析能力

Core 不预制所有 App 方言的业务行为。

例如 Data Derived、数据推送、血缘追踪等，都属于具体方言的语义。

Core 提供通用的函数分析基础，具体方言通过扩展 Function 的语义分析能力，提供自身行为的解释。

因此，一致性分析应当是开放、可扩展的能力，而不是一套固定的业务规则。

## 3. 分析范围

采用分级分析，优先处理影响较大的语义。

### 第一级：基础结构一致性

现有加载机制已经能够处理大部分确定性约束：

- 类型与属性合法性
- 关系引用
- 函数参数和返回类型
- 基础结构冲突

这部分不作为新的主要工作方向。

### 第二级：App 内部一致性

分析同一个 App 内部的函数及数据行为：

- 字段之间的业务约束
- 函数的数据读取与修改范围
- 多个函数对同一数据的影响
- 数据派生与汇总之间的依赖
- 不同操作是否可能违反共同约束

例如：

`balance >= 0` 是账户的整体业务约束。

所有可能修改 balance 的函数，都应该纳入分析，而不是由每个函数单独重复定义这个约束。

### 第三级：跨 App 一致性

进一步分析：

- App 之间的外键关系
- 数据读取和写入依赖
- 数据推送与事件触发
- 工作流之间的状态变化
- 跨 App 函数组合产生的影响
- 视图对业务语义的解释是否一致

视图呈现类属性（例如 displayOnly）影响较低，可以降低分析优先级。

### 第四级：整体业务意图一致性

分析多个 App、函数、工作流组合后，是否存在违反系统整体约束的行为。

重点不是证明每个函数正确，而是检查它们组合起来是否共同遵守已声明的业务规则。

## 4. Runtime 设计方向

一致性分析不应是一次性的全表扫描，而应成为 Runtime 的持续状态维护能力。

考虑建立一个运行时语义依赖网络：

- 注册进入 Runtime 的类型、App、方言实体及函数，参与相关分析。
- 语义对象提供自身的依赖和影响信息。
- 函数分析能力向 Runtime 暴露数据影响及相关约束。
- Runtime 维护对象之间的语义依赖关系。
- 类型、函数、关系等发生修改时，主动触发相关推导。
- 只重新分析受到影响的部分。
- 持续更新整体一致性状态。

最终 Runtime 不仅持有语义定义和执行能力，还持有当前语义空间的整体分析状态。

### 冲突记录

冲突信息作为 Runtime 中可以持续更新的状态，而不是一次分析的临时返回值。

记录内容包括：

- 涉及的语义对象
- 相关函数及依赖路径
- 冲突的业务约束
- 判定依据
- 影响范围
- 当前判定状态

需要考虑循环依赖、增量传播、版本管理和分析结果的原子更新。

## 5. 冲突判定原则

一致性分析负责发现问题，不负责自动修复业务。

区分不同判定结果：

| 类型 | 含义 |
|---|---|
| 确定冲突 | 已明确违反语义约束 |
| 潜在冲突 | 存在违反约束的可能 |
| 信息不足 | 当前无法完成判断 |
| 待人工确认 | 可能是合法的业务例外 |

分析结果主要作为警告和决策依据。

是否拒绝执行、修改工作流、调整业务规则或由人工补充定义，由相应的编辑或执行机制决定。

## 6. 与传统软件工程的边界

执行层的时序、并发、事务、外部系统交互及具体业务规则，仍然由人类开发者负责设计和验证。

这些工作依然需要传统测试和长期工程迭代。

语义一致性分析解决的是另一类问题：

**AI 生成的多个局部语义定义，组合起来是否仍然表达一个一致的系统。**

它不取代传统软件测试，也不承诺证明所有运行时行为正确。

## 7. 与 AI 的关系

AI 逐渐接管 App、Function、Workflow 等语义开发后，需要独立的语义约束机制。

预期形成：

AI 构造和修改语义  
→ SchemaNode 编译及一致性分析  
→ Runtime 更新整体语义状态  
→ 冲突反馈给 AI 或开发者  
→ 修改并重新分析

AI 负责语义开发，SchemaNode 负责语义约束，执行层负责确定性实现。

一致性分析是 AI 语义开发的重要质量门槛。

## 8. 实施原则

- 不引入独立的通用形式化验证体系。
- 优先复用现有 Function、CompileContext 和多目标编译机制。
- 从函数影响分析开始，不追求一次覆盖全部语义。
- 优先分析数据写入、状态变化、事件和工作流等高影响行为。
- 采用开放式方言扩展，不预制所有业务行为。
- 采用增量推导，不依赖全量扫描。
- 明确区分确定冲突、潜在风险和无法判断的情况。
- 随着 AI 语义构造能力扩大，逐步扩展分析覆盖范围。

## 9. 长期愿景

SchemaNode Runtime 从可执行语义环境，进一步发展为能够持续理解、分析和维护整体语义状态的环境。

它不仅知道系统如何执行，还能分析系统中不同意图之间的关系，以及它们是否共同成立。

这是 SchemaNode 向软件工厂能力扩展的一个重要方向。

**核心原则：让整体一致性分析从已有语义机制中自然涌现，而不是为了实现验证功能，另行构造一套独立范式。**
