# 05. 语义方言

前一章介绍了**定义域**和**公共语义共识**。

定义域解决的是如何定义、组合和处理语义；公共语义共识则约定了不同执行层之间需要共同理解的基本语义能力，包括共有的原型、类型、属性和函数。

但公共语义共识并不意味着所有执行能力都必须被统一。

例如，数据类型、属性、关系、函数等属于比较基础的公共语义，而应用容器、权限、工作流、ETL、事件处理等，则往往与具体的执行环境有关。

如果这些能力最终仍然回归代码，那么语义与执行代码之间的耦合依然存在。

因此，在公共语义共识之上，还需要一个能够承载特定执行能力的层次：

> 将一类稳定的执行能力及其可变结构，从代码实现中提取为可描述、可组合、可执行的语义原型族。

这就是**语义方言（Semantic Dialect）**。

---

## 1. 语义方言的定义

语义方言建立在公共语义共识之上，根据特定的执行需求，进一步定义一组具有明确执行含义的语义原型族。

这里需要特别注意：“方言”不是按照行业领域划分的。

医疗、金融、农业、制造不是方言，它们只是业务语义的不同组合。真正的方言对应的是执行能力的抽象——比如 App 方言提供 Application、Field、Workflow、Event、Permission 这些执行环境本身的能力。

因此，语义方言更接近于：

```text
公共语义共识
    ↓
执行能力抽象
    ↓
语义原型族
    ↓
具体业务语义
```

它把原本隐藏在程序框架、基础设施和执行代码中的一部分能力，提升为可以被语义描述的对象。

业务领域只是这些语义能力的一种具体组合。因此，同一个 App 方言可以用于碳汇系统、医院管理系统、制造管理系统、财务系统——因为它定义的是执行能力，不是业务知识。

>业务领域描述“处理什么”，语义方言描述“依靠什么执行能力来处理”。

---

## 2. 从公共语义到执行能力

公共语义共识提供的是不同执行层都可以理解的最小语义基础。

例如：

```text
node
├── scalar
├── struct
├── array
├── function
└── ...
```

以及：

```text
Property
Relation
Function
```

这些语义可以被不同执行层共同解释。

但仅有这些能力，并不足以构建一个完整的应用执行环境。

例如：

```text
一个用户可以登录应用
一个应用包含多个数据表
数据表可以配置行级权限
用户操作可以触发工作流
工作流可以调用函数
事件可以触发数据处理
```

这些语义并不是 struct、array 或 function 本身能够表达的。

如果采用传统程序设计方式，这些能力通常会进入框架代码：

```text
ApplicationService
PermissionService
WorkflowService
EventHandler
...
```

于是业务语义最终又需要通过代码调用这些服务。

语义方言所做的事情，是把其中稳定的执行能力和可变部分分离出来。

```text
传统执行框架

代码
 ├── Application
 ├── Permission
 ├── Workflow
 ├── Event
 └── ...
```

转化为：

```text
语义方言

公共语义共识
    ↓
App 方言
 ├── Application
 ├── Field
 ├── Workflow
 ├── Event
 ├── Permission
 └── ...
    ↓
业务语义
```

其中原型负责规定语义结构和执行能力，而具体业务只需要声明这些能力如何组合。

这意味着：

执行能力本身仍然由执行层提供，但执行能力的使用方式不再必须通过代码表达。

---

## 3. SchemaNode App 语义方言

SchemaNode Core 提供的是公共语义定义域，而 SchemaNode App 则是在此基础上构建的一套具体语义方言。

例如，App 方言提供以下语义原型：

### 3.1 App

App 是应用执行环境中的容器。

它可以根据配置确定：应用边界、租户隔离、组织上下文、用户上下文、应用级权限。

这些能力本身由执行层实现，但其配置和组合方式可以通过语义进行描述。

### 3.2 App Field

App Field 是应用中的逻辑数据对象。

它可以通过语义配置：数据字段、字段类型、数据关系、数据来源、物理表映射、视图映射、数据权限。

因此，App Field 并不等价于传统数据库中的 Table。它更接近于：

> 应用执行环境中，一个可被语义描述和处理的数据实体。

其最终可以映射到数据库表、视图，甚至其他数据来源。

### 3.3 Workflow

Workflow 是 App 方言提供的流程执行能力。

```text
Event
  ↓
Workflow
  ├── 条件
  ├── 数据处理
  ├── 函数调用
  └── 状态变化
```

传统应用通常需要通过 Workflow Engine、Controller 或 Service Code 来完成这些逻辑。而在 App 方言中，这些可变部分可以成为语义结构的一部分。

### 3.4 Event

Event 用于描述执行环境中的触发条件：数据创建、数据修改、数据删除、用户操作、定时触发。

具体的 Event 类型可以由方言继续扩展。因此 Event 本身并不是公共语义共识中的基本概念，而是 App 执行环境提供的一种语义能力。

---

## 4. 方言中的语义属性

语义方言不仅可以定义新的原型，也可以基于公共原型增加新的语义属性。

例如 App 方言中的权限能力：

```text
App
 └── Auths

App Field
 └── Row Auth
```

其中 Auths 可以描述应用级权限，而 Row Auth 则可以描述数据行级访问控制。

这些能力并不需要修改公共的 node、struct 等基础语义。它们只是将新的 Property 附加到已有的语义原型上。

```text
公共语义
    ↓
node.struct
    ↓
Property
    ↑
App 方言扩展
```

方言并不需要重新定义整个语义体系，而是在公共语义之上增加自己的执行能力。这也是语义原型具有可扩展性的原因。

---

## 5. 从程序框架到语义基础设施

从这个角度看，语义方言实际上是在重新划分过去程序框架中的一部分职责。

传统程序框架通常直接提供：CRUD、权限、ETL、Workflow、Event、任务调度、数据访问。这些能力以 API、Service、Controller、Middleware 等形式存在。业务代码通过调用这些 API 完成实际需求。

而语义方言则尝试将其中稳定的执行能力抽象成语义原型，将其中经常变化的部分转化为语义声明。

```text
传统方式

业务需求
   ↓
业务代码
   ↓
框架 API
   ↓
执行能力
```

而语义方言希望形成：

```text
业务需求
   ↓
业务语义
   ↓
语义方言
   ↓
执行能力
```

执行层依然存在。区别在于：

> 业务变化不再必须通过修改执行代码来表达，而可以通过语义声明改变。

因此，语义方言并不是把程序框架简单“配置化”。它更准确地说，是：

> 将一类可复用的执行能力提升为语义空间中的一组可描述、可组合、可执行的原型。

---

## 6. 方言本身也是一种语言
如果公共语义共识是所有执行层共同理解的基础，那么语义方言就是在这个基础上形成的具体语言。

```text
   公共语义共识
        ↓
    Semantic
        ↓
   ┌────┴────┐
   ↓         ↓
App Dialect  其他 Dialect
   ↓
Application
   ↓
具体业务语义
一个方言拥有自己的原型、Property、Relation、Function 和执行规则。因此它本身也是一种语言。只是它不是从零开始定义语言，而是建立在公共语义共识之上。

这也是“方言”这个名称的含义：

> 它共享公共语义的基本词汇和语法能力，同时针对特定执行环境增加自己的表达能力。

---

## 7. 语义方言与执行层
语义方言并没有消除执行层。

```text
App Workflow
      ↓
Workflow Runtime

App Field
      ↓
Data Provider

    Auth
      ↓
Permission Runtime

  Function
      ↓
Function Provider
```

方言定义的是：这些执行能力如何被语义描述、如何被组合、哪些部分允许变化。

执行层负责：如何解释、如何执行、如何访问资源、如何与外部系统交互。

因此，语义方言仍然遵循前面建立的原则：

```text
语义
  ↓
执行
```

而不是：

```text
业务语义
  ↓
直接绑定
  ↓
某一套具体代码
```

这使得同一套方言理论上可以拥有不同的执行层实现。

---

## 8. 方言之间的关系
如果不同执行环境都建立在同一公共语义共识之上，那么它们之间并不需要共享全部语义。

```text
                公共语义共识
                      │
          ┌───────────┼───────────┐
          ↓           ↓           ↓
       App 方言    Data 方言    Workflow 方言
          │           │           │
          ↓           ↓           ↓
       应用执行层   数据执行层   流程执行层
```

不同方言可以独立定义自己的原型、扩展 Property、定义 Relation、提供 Function、发展执行层。只要它们仍然遵守公共语义共识，就可以在更高层形成组合。

这也意味着，未来一个完整的系统未必只能使用一个方言。例如：

```text
App
 ├── Data
 ├── Workflow
 └── Permission
```

其中不同能力可以来自不同的语义方言，并通过公共语义进行组合。

---

## 9. 从公共共识到业务语义
至此，前面的几层关系可以完整连接起来：

```text
  定义域
    ↓
公共语义共识
    ↓
 语义方言
    ↓
 业务语义
    ↓
具体语义实体
```

其中：

**定义域**：解决如何定义语义。

**公共语义共识**：解决不同执行层之间哪些基础语义必须能够共同理解。

**语义方言**：解决某类执行环境如何进一步提供可描述、可组合的执行能力。

**业务语义**：则是在这些能力之上，真正描述具体业务对象、规则和流程。

因此，业务开发最终不再需要从代码开始：

```text
需求
 ↓
业务代码
 ↓
框架
 ↓
执行
```

而可以逐渐转化为：

```text
需求
 ↓
业务语义
 ↓
语义方言
 ↓
公共语义
 ↓
执行层
```

这也是语义与执行分离之后，进一步产生的一个结果：

> 执行能力本身也可以成为语义。

---

## 10. 尚未解决的问题
语义方言解决了公共语义之上的扩展问题，但也引出了三个尚未解决的问题：

* 组合问题：不同方言之间如何组合？App 方言的 Workflow 调用 Data 方言的处理能力时，共享哪些语义？

* 发现问题：一个执行层支持某个方言，其他执行层如何知道它支持哪些原型、Property、Relation 和 Function？

* 兼容问题：不同执行层提供了语义等价但实现不同的方言时，如何保证互操作？

这些问题已经超出单个执行层内部的定义范围，进入语义协议的领域。

在当前阶段，SchemaNode 主要解决的是：

> 如何在一个可执行定义域中，建立公共语义，并在其上构造可以真正运行的语义方言。

至于不同执行层之间如何交换和协商这些语义，则留给后续的协议层讨论。
