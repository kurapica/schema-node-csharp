# SchemaNode

> **可执行结构化语义语言（Executable Structured Semantic Language）**
> 一个正在从语义实体结构化描述，走向公共语义共识与多维语义空间的底层内核。

SchemaNode 不是低代码平台、表单引擎、ORM 或 API 文档工具。它尝试在现有系统之上建立一个**可执行的语义层**。

## ⚡ 核心特征

**SchemaNode 不是把业务规则写得更快，而是尝试让业务语义本身成为可以被描述、组合和执行的结构。**

* **语义与执行分离**
  业务语义以结构化定义存在，具体执行由执行层负责。执行层可以独立演进，而无需将业务规则重新实现一遍。

* **可组合的语义基础**
  以 **Meta / Property / Relation / Function** 作为目前的基础语义原语，通过组合构造更高层的语义类型和语义方言。

* **公共语义共识**
  不同语义方言建立在共同的结构化语义基础之上，使语义定义本身也可以被描述、处理和交换。

* **确定性的语义执行**
  同一语义定义可以被不同执行层解释，用于验证、查询、权限过滤、ETL 或执行树生成，执行遵循语义是唯一真相原则。

> **SchemaNode 不试图预先规定所有领域的业务语义。**
> 它探索的是一套能够定义、承载和执行不同语义的共同基础。

## 🎯 一个真实系统中的实践

SchemaNode 的设计并非完全从理论出发。

在一个农业碳汇认证系统中，系统包含约 200 个参数表、300 个输入表和 200 个汇总表，前端需要处理类似 Excel 的复杂数据关联与约束，后端则需要保证计算过程透明、结果可追溯；同时，认证标准会持续更新，新规则需要能够加入而不影响已经完成的历史项目。

在这样的约束组合下，4 人团队在 3 个月内基于语义和执行分离的设计原则完成了一期系统的构建，构建了一个随着语义积累而加速需求迭代的系统。

这里真正值得关注的并不是团队规模，而是这些复杂度最终如何被表达。

当数据结构、约束、关联关系和计算规则能够使用统一的结构化语义描述时，它们不再需要分别实现和维护于数据库、后端、接口和前端。

这也是 SchemaNode 继续探索的起点：

> 如果复杂度来自大量语义之间的组合，而不是某一种具体技术，那么能否直接让这些语义成为系统的基本结构？

## 🧬 四原语与多维语义空间

SchemaNode 目前将实体的基础语义拆分为四种原语：

* **Meta**：描述实体是什么，以及如何构成；
* **Property**：描述实体具有的可组合属性；
* **Relation**：描述实体之间的关系，以及关系产生的语义；
* **Function**：描述语义的执行意图，具体实现由执行层提供。同一个语义函数可以根据使用目的参与推理、查询、权限过滤或生成其他执行形式。

它们并不是对所有语义的最终分类，而是一组用于组合语义实体的最小基础。

通过这些原语，可以从简单的数据结构逐渐构造出具有约束、关系和行为的**语义类型**。

### 一个极简的语义类型

传统代码中，一个 `minMax` 类型可能只是：

```jsonc
{
  "min": 0,
  "max": 100
}
```

看到这里，我们很容易认为：

* min 表示最小值；
* max 表示最大值；
* max 不能小于 min。

但这些含义其实并不是 `number` 或这个结构本身提供的，而是程序员通过命名和约定赋予它的语义。

不妨把字段名换成更常见的：

```jsonc
{
  "a": 0,
  "b": 100
}
```

数据结构完全没有改变，但我们已经无法仅凭这个结构知道：

* a 是什么？
* b 是什么？
* 两者之间有什么关系？
* b 是否必须大于 a？

于是，这些信息就必须继续存在于程序员的约定、注释、前端代码或后端验证代码中。

SchemaNode 尝试做的，是让这些原本依赖约定的语义直接成为定义的一部分：

```jsonc
nodeType: {
  namespace: "test",
  name: "minMax",
  kind: "struct",

  struct: {
    fields: [
      { name: "a", type: "number", display: "最小值" },
      { name: "b", type: "number", display: "最大值" }
    ],

    relations: [
      {
        target: "b",
        property: "lowlimit",
        call: "system.intrinsic.assign",
        args: [{ source: "a" }]
      }
    ]
  }
}
```

这里并没有编写一个专门的 `minMax` 验证器。

> `a`、`b` 的结构由 **Meta** 描述，显示语义由 **Property** 描述，而 `a → b.lowlimit` 的约束则由 **Relation** 表达。

因此，执行层不需要认识 `minMax` 这个业务类型，只需要理解这些公共语义。

> **从“程序员知道它是什么意思”，到“定义本身携带它是什么意思”。**

这也是 SchemaNode 从传统数据类型走向**语义类型**的一个基本例子。

## 🧩 语义方言

SchemaNode 不试图建立一套覆盖所有领域的固定业务语言。

不同领域可以在公共语义基础上定义自己的**语义方言（Semantic Dialect）**，也可以理解为用于定义领域语义实体的 Schema DSL。

语义方言可以定义：

* 什么样的对象构成领域实体；
* 实体可以具有哪些属性；
* 属性具有什么约束；
* 实体之间存在什么关系；
* 这些语义如何被执行层解释。

因此，方言负责扩展领域语义，而执行层负责解释和执行这些语义。

---

## 🌐 公共语义共识

无论是业务 Schema，还是用于定义 Schema 的 Schema DSL，本身都是结构化数据。

因此，公共语义共识关注的并不是“所有领域应该使用哪些业务语义”，而是：

> **一套结构化语义，需要哪些共同的基础能力，才能被完整地定义、表达和处理？**

这些基础能力构成 SchemaNode 的公共语义基础。

它覆盖的不只是数据类型，还包括属性、关系、函数，以及这些定义本身的结构和处理方式。

因此，Schema DSL 本身也可以成为 SchemaNode 能够描述和处理的结构化语义。

由此可以形成：

**公共语义共识 → 定义语义的共同基础**
**语义方言 → 面向领域的语义扩展**
**执行层 → 对语义进行具体解释和执行**

不同方言可以拥有不同的领域语义和执行方式，但可以在共同的结构化语义基础上进行理解、转换和交换。

## 📂 当前开源状态

当前开源版本包含：

* **语义内核**：分别提供 **C#** 和 **TypeScript** 两个执行层实现，用于解释和执行公共语义。
* **App 方言**：面向通用数据处理与权限管理，可嵌入微服务，也可以独立运行，目前已用于验证 CRUD、权限、数据关联、ETL 等应用执行能力。
* **语义编辑器**：用于配置语义类型及其验证规则。语义定义可以推送到各执行平台，实现业务语义的即时更新。

语义编辑器本身也是一个执行层。

它并不针对每一种业务类型编写特殊代码，而是基于公共语义共识解释语义。因此，执行层可以独立演进，也可以被其他实现替换，而不需要改变已经建立的业务语义。

> **执行层不需要认识具体业务，只需要理解共同的语义基础。**

目前的 App 方言和编辑器主要用于验证语义内核的实际执行能力；它们并不是 SchemaNode 最终要定义的业务范围。当然，它们已经经过企业级的验证和使用，证明了其有效性。

## 🔮 从这里开始

SchemaNode 目前并不是一个已经完成的“多维语义空间”。

我们只是从**语义实体的结构化描述**开始，建立了一套可以运行的语义内核，并在部分真实应用场景中进行了验证。

接下来仍有大量问题需要探索：

* 哪些语义应该成为公共语义共识？
* 哪些能力应该由语义方言扩展？
* 不同领域的语义如何组合和交换？
* 当语义维度不断增加后，如何由机器和 AI 协助维护和操作？

这些问题，也是 SchemaNode 继续发展的方向。

> **我们目前只是打开了多维语义空间的一小部分。**
>
> 但即使是这一步，也已经足以让一些原本隐藏在代码中的语义，成为可以被描述、组合、执行和积累的结构。
>
> **真正的多维语义空间，还有待继续探索。**
