# 01. 语义原型与定义域

开始阅读本系列前，建议先阅读[架构章节](../architecture/01-why.md)。如果仅限于使用而不关注原型实现，也可以跳过Core文章，直接阅读 App 相关的章节即可。

本章从实践出发，依次介绍语义实体、语义类型与语义原型，并进一步说明定义域和公共语义空间的关系，为下一章介绍 SchemaNode.Core 的 `node` 原型族建立基础。



## 语义实体（Entity）

在架构文档中，我们将语义实体定义为：**结构化数据及其相关语义属性共同构成的整体。**

语义实体可以在不同执行层之间传递，但各执行层的实现形式未必相同。跨执行层交换时，可以只传递结构化数据，再由各执行层结合相应的语义类型及其支持的语义属性，恢复并处理完整的语义。

例如，一个表示年龄的语义实体，在前端执行层中可以具有如下形式：

```json
{
    "value": 55,
    "properties": {
        "display": "年龄",
        "unit": "岁",
        "type": "number",
        "lowlimit": 0,
        "uplimit": 100,
        "expectation_life": 80
    }
}
```

其中，**结构化数据负责承载值，语义定义负责赋予值以可解释的含义。**

这里的语义属性具有不同的来源。

`display`、`unit`、`type`、`lowlimit` 和 `uplimit` 描述了年龄这一语义类型的通用特征。对于同一语义类型的实体，这些属性通常具有相同的定义，因此可以由语义类型提供，我们将其称为**静态属性**。

而 `expectation_life`（预期寿命）则不同。它无法仅凭年龄这一字段的类型确定，还可能依赖性别、生活环境、生活习惯等上下文信息。此类属性需要通过关联其他语义信息计算得到，我们将其称为**动态属性**。

需要注意，静态与动态描述的是属性的来源及其确定方式，而不是属性本身的固定分类。

各执行层之间只传递`55`这个数据，其余的属性则基于上下文即语义类型恢复。

---

## 语义类型（Type）

语义类型是对同类语义实体的抽象。它不仅描述实体的数据结构，还定义适用于该类型的静态语义属性，以及计算动态属性所需的关联关系。

从组成上看，语义类型需要提供三个方面的能力：

- **结构（Meta）**：描述实体的数据结构，以及各组成部分的类型。
- **静态属性（Property）**：描述实体或其组成部分具有的通用语义特征。
- **关联（Relation）**：描述语义信息之间的依赖关系，以及如何基于关联计算或派生相应的语义属性。

这三个方面共同构成语义类型的基础。

考虑一个具体例子：年龄是人的组成部分，而预期寿命需要结合人的性别等信息才能确定。因此，预期寿命的关联定义不一定属于年龄自身的类型，而可以定义在人的语义类型中，并将年龄指定为关联属性的目标。

换句话说，**语义属性可以附着在局部实体上，而决定该属性的关联可以定义在更大的实体中。** 关联由此能够利用上层实体提供的上下文信息。

为了让不同执行层能够交换和解释语义类型，我们需要一种统一的语义类型声明格式。

例如，可以用如下声明描述人的语义类型：

```jsonc
{
    "type": "struct",
    "display": "人",
    "fields": [
        {
            "name": "name",
            "type": "string"
        },
        {
            "name": "gender",
            "type": "string",
            "whitelist": [
                "男",
                "女"
            ]
        },
        {
            "name": "age",
            "type": "number",
            "display": "年龄",
            "unit": "岁",
            "lowlimit": 0,
            "uplimit": 100
        }
    ],
    "relations": [
        {
            // 为年龄提供预期寿命属性，示例中仅根据性别计算
            "target": "age",
            "property": "expectation_life",
            "calc": "getexpectlifefromgender",
            "args": [
                {
                    "source": "gender"
                }
            ]
        }
    ]
}
```

这里，`struct` 描述申明这个语义类型的结构，字段声明提供各字段的类型与属性，`relations` 则描述如何为年龄关联预期寿命属性。

具体的属性名称、参数格式与关联声明规则，取决于所采用的语义定义体系。上例用于说明语义类型的基本组成，而不是完整的声明规范。

只要执行层能够识别并解释这套声明格式，并支持其中涉及的语义能力，就可以根据同一份语义定义处理相应的实体，而不必为每一个具体的语义类型编写专门的处理逻辑。

由此引出下一个问题：执行层如何识别语义类型的结构，判断其支持的语义属性，并以相应的方式解析和消费这些声明？

这正是语义原型需要解决的问题。

---

## 语义原型（Prototype）

如果要求执行层为每一种语义类型单独实现处理逻辑，那么语义类型的数量越多，执行层需要维护的专用代码就越多。

尤其是在跨系统交互中，执行层经常会遇到自身开发时尚未预见的语义类型。若每次遇到新类型都需要修改执行层，语义层与执行层的分离便失去了意义。

因此，我们需要进一步抽象语义类型，按照其结构及语义特征，将其归纳为有限种可识别的类别。

例如，`enum`、`struct`、`scalar` 等类型，可以分别描述枚举、结构化数据和标量数据。执行层不必预先认识每一种具体类型，只需要理解这些类型所属的语义原型，以及相应原型支持的语义能力。

我们将这一层抽象称为**语义原型（Prototype）**。

语义原型的数量远少于具体语义类型。以 SchemaNode.Core 为例，目前共有 32 个原型定义；排除 `node.string.usage` 这类用于附着或扩展其他定义的原型后，核心原型约有 17 种。

对于执行层而言，这是一组规模相对有限、可以独立实现和维护的契约。 这意味着，即使未来业务系统膨胀出成千上万个语义类型，执行层需要维护的底层逻辑复杂度依然维持在几十个原型的量级。

语义原型的核心作用是连接语义声明与执行层处理逻辑：

1. 语义类型基于原型声明自身的结构及语义特征。
2. 执行层识别原型，并按照约定解析语义类型。
3. 执行层根据自身具备的能力，解释和消费相应的语义实体。

因此，语义原型不是具体业务逻辑的集合，而是执行层理解语义类型的依据。如果我们将本质复杂度归于语义层，偶然复杂度归于执行层，那么原型就是两者间的最小耦合。

例如当我们给定一个语义属性`visible`时，如果执行层无法理解和处理它，那么必然被忽略，因为我们很难再引入一个新的概念去描述`visible`为可见性，所以，可以被执行层执行的属性必然是它基于原型可以识别的。

需要注意，**原型名称本身并不是跨执行层契约的关键。** 名称只是执行层识别原型的一种方式，不同执行层可以使用不同的内部名称或实现形式。真正需要保持兼容的是原型所描述的结构与语义约定，而不是所有执行层都采用相同的原型名或代码实现。

SchemaNode.Core中提供的`node`原型族，理论上只要能覆盖所有公共语义原型，就可以被替换掉，而不影响已有语义类型的解析和执行，所以设计上会避免这种上帝执行层的存在风险，尽管它是目前的核心实现。

语义原型本身也需要被定义。它既要描述所支持的类型结构，也要描述这些类型可以使用的语义属性及其约束。与此同时，语义属性也可以声明自身适用的语义原型，从而让类型与属性之间形成明确的约束关系。

这里还有一个重要特点：**语义原型的定义本身，也可以使用结构化语义类型来表达。**

这意味着，我们不必再为语义原型设计一套完全独立的定义体系，不需要在代码里硬编码一套特殊的元语言。。原型可以由它所支持的语义类型描述，语义类型又可以基于原型构造，由此形成自举结构。

下一章将具体介绍 SchemaNode.Core 如何通过 `node` 原型族实现这一机制。

> 注意，虽然数据处理域中，每个语义类型只基于一个原型，但设计上，并没有主动限制语义类型的原型数量，某个意义上可以将原型看作一种接口，语义类型实际可以实现多个接口。如果我们将物理世界的实体引入，例如一个杯子，它可以同时具有`容器`, `易碎品` 等多个原型，例如`易碎品`原型可以提供最大承压力等属性描述。

> 实际之后碰到的结构体字段就是多原型解释，例如它首先具有围绕字段设计的属性`visible`, `require`等，基于字段的类型，还可以具有该类型对应的原型属性，例如字段使用枚举值，那么`root`根植，`cascade`级联限制等属性就可以被应用到字段上。

> 原型在这个设计中，更多是属性的附着点。代表了属性值如何被解析和消费。

## 定义域（Definition Domain）

定义域关注的是一个特殊的问题空间：**语义类型本身应该如何被定义。**

前面介绍的语义类型主要用于描述业务实体，而定义域则负责描述语义类型的声明规则，包括可以使用哪些原型、可以附着哪些属性，以及如何组织相应的结构和关联。

**定义域关注的是语义的声明与构造，而不是业务语义的具体执行**。

在 [SchemaNode Man](https://kurapica.github.io/schema-node-man/#/app) 中尝试定义语义类型时，可以观察到这一点：编辑界面会根据当前选择的语义原型，呈现相应的字段、选项、显示与隐藏规则，以及其他约束。

这些界面行为并不是针对所有语义类型预先编写的独立表单，而是由语义原型及其相关属性共同决定的。它本质只是消费`node`原型，其余原型则作为`node`的扩展属性来实现。

这与在 IDE 中编写程序类似。编程语言决定了可以声明哪些结构、使用哪些语法，以及在出现错误时如何提供提示；定义域则决定了语义类型可以如何声明，以及声明是否符合相应的语义规则。

两者的区别在于，定义域处理的对象是语义类型的声明，而不是语义类型所描述的业务数据。

因此，定义域通常由能够生成语义类型声明的执行层处理。例如，语义类型可以通过专用编辑器、配置工具，甚至程序代码生成。它们不必采用相同的实现方式，只要最终产生的语义声明满足相同的兼容约定，就可以被其他执行层消费。

还需要注意，**定义域中用于描述语义类型的类型，与业务数据交互时使用的类型，并不一定是同一组类型。**

前者用于构造和约束语义声明，后者用于描述和处理业务实体。两者可以共享公共语义基础，但承担不同的职责。

## 公共语义空间（Public Semantic Space）

公共语义空间是一个逐步形成的概念。它所要解决的问题是：当不同执行层需要交换结构化数据及其语义定义时，如何提供一套共同遵循的机制，使各执行层能够理解和消费彼此声明的语义。

在这一过程中，需要区分两类不同性质的实体。

一类是具有普适性的数据类型实体，例如订单详情、工作流执行状态等。这类实体主要用于表达业务数据及其语义，其结构和语义定义可以脱离特定的执行环境而被理解。它们的 Meta、Property 及其关联的语义关系，可以成为不同执行层共同遵循的基础。

另一类是方言中的功能性实体，例如订单、工作流、应用本身等。这类实体不仅承载数据，还与特定的业务领域、组织范围或执行机制相关联。订单状态的流转、工作流的执行方式、应用的数据存储机制等功能，通常需要执行层结合相应的 Meta、Property 及其他配置进行解释和执行。这些实体的语义往往依赖特定的领域约定或执行能力，不能仅凭通用元数据就获得完整、普适的解释。

两类实体的区别不在于是否包含 Meta 和 Property，而在于其语义能否脱离特定的方言与执行机制，被不同执行层共同理解。公共语义空间主要关注前一类实体及其语义定义；后一类实体则更多由方言定义，并由相应的执行层提供具体能力。

这并不意味着两类实体必须相互隔离。方言完全可以基于公共语义原型构造新的语义类型，并进一步定义领域特有的属性、关系和功能。公共语义提供可共享的基础，方言则在此基础上扩展特定领域的语义与执行能力。

这也引出了公共语义空间的核心机制：**通用语义原型（General Semantic Prototypes）**。

这并不要求所有执行层使用相同的技术栈、内部模型或执行逻辑，而是要求它们对共享的语义基础形成一致的理解。

只要不同执行层能够理解公共语义原型，就可以解析基于这些原型构造的语义类型，而不必针对每一种具体类型分别开发适配逻辑。下一章介绍的 SchemaNode.Core node 原型族，正是这一机制的具体实现。

除了公共原型外，公共语义空间也提供常用类型，以及系统级语义原子函数用于覆盖数据转换处理。

基于公共原型和常用语义类型，可以覆盖数据处理领域，这也确保了不同执行层交换数据时的兼容性。

需要强调的是，公共语义空间不意味着每个执行层都必须实现全部能力。一个执行层只需要处理自身职责范围内、能够解释和消费的语义。只要共享部分遵循一致的约定，其他语义就可以由相应的执行层独立处理。

## 语义方言（Dialect）

在上面的讨论中，无法脱离执行层的语义原型就是该领域中的一些核心概念，也对应该领域的**语义方言**。

原型只是剥离了这些概念的可变部分，执行部分则由执行层负责实现。

这是一种前期投入较大、但能够随着语义积累逐步降低后续构造成本的范式。

针对特定问题域形成的原型族及其配套语义约定，可以构成一组**语义方言（Dialect）**。

因此，公共语义空间与语义方言承担不同的职责：

- **公共语义空间**提供跨执行层共享的基础语义约定。
- **语义方言**在公共基础之上，进一步描述特定问题域的语义结构与能力。
- **执行层**根据自身的职责，实现公共语义和相关方言所约定的处理能力。

公共语义提供共同的基础，语义方言则允许不同领域继续扩展。两者相互配合，使语义体系既能够跨执行层协作，又不必将所有领域的语义强行收敛为一套固定标准。

不同组织针对同一问题域可以构造不同的语义方言。它们不必采用相同的领域模型或执行方式，但可以通过公共语义空间交换兼容的数据与语义定义。当然，如果以社区形式发展，一个领域的方言如果被统一定义，则可以在公共语义层上构建领域公共语义层，形成多层级语义空间体系，加速领域内的语义交换。

下一章将从 SchemaNode.Core 的 `node` 原型族开始，具体说明公共语义原型如何被定义，以及语义类型如何通过这些原型实现自举。
