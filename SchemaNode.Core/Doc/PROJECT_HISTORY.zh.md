# SchemaNode 项目历史

> 一次失败的暖通报价系统如何催生了一个将 100 人月工作压缩至 9 人月的元数据驱动平台。

---

## 序幕：暖通报价系统的灾难（~2019）

SchemaNode 的起源可以追溯到深圳一个看似简单的项目：将一套基于 **5,000 个 Excel 表格** 的报价系统转换为 Web 服务。客户需要按项目通过浏览器界面输出报价数据。

当时的技术方案似乎合理：
- **Schema** 定义数据结构
- **Lua** 作为嵌入式脚本语言处理业务逻辑和数据转换

系统完成了，但结果是**灾难性的**：
- Lua 脚本在数千个配置点之间演变成无法管理的命令式逻辑网络
- 调试单个数据问题需要追踪多层动态脚本执行，完全没有静态分析能力
- 团队无法自信地进行任何修改，因为害怕连锁故障
- **系统从未上线。**

### 经验教训

1. **图灵完备的脚本语言是模式层业务逻辑的错误工具。** 它们过于强大而无法分析，过于灵活而无法约束，过于不透明而无法审计。
2. **模式系统必须是语义可分析的。** 如果无法在不执行的情况下理解一段配置的*含义*，维护就是不可能的。
3. **唯一真相，多种解释。** 同一条业务规则应该可以编译成不同的执行形式（验证、过滤、转换），而无需重写。

## 第一版：Datanode — 农业碳汇核算系统（2021）

### 挑战

2021 年，一个新项目出现：**农业碳汇核算系统**。约束条件极其苛刻：

| 约束 | 详情 |
|------|------|
| 团队规模 | **3 人**（1 前端、1 后端、1 架构/建模） |
| 数据表 | 第一阶段约 700 张数据库表 |
| API 数量 | 传统做法需要约 3,000 个 API，即使统一参数表逻辑也约需 2,000 个 |
| 数据复杂度 | 跨表依赖无处不在：作物选择限制肥料种类，肥料参数来自农场关联，单一输入表单可有 100+ 数据关联 |
| 时间线 | 3 个月交付第一版 |

传统开发方式在数学上是不可能的。即使参数表逻辑统一，仍有约 500 张业务表——每张表需要 CRUD API（4 个/表 = 2,000 个 API），外加跨表数据关联逻辑。

### 解决方案：Datanode

SchemaNode 的前身诞生了。它只包含四个核心模块：

1. **数据结构定义** — 声明数据类型（结构体、枚举、标量）及其字段
2. **数据关系定义** — 定义数据字段之间的关联，包括跨表查询
3. **函数定义** — 声明带参数和返回类型的纯函数，用于数据转换
4. **App 与 App Field** — 将数据结构映射到应用字段，配置显示和存储

### 开发模式

这四个模块催生了一种革命性的开发范式：**三线并行开发，零沟通成本**。

```
前端开发者                  Schema 建模师              后端开发者
─────────────             ──────────────             ──────────────
布局与步骤                 数据结构定义                项目管理
UI 组件                    数据关系定义                微服务
表单导航                   函数定义                    ~40 个 API
                           App/Field 配置             基础设施
```

关键特征：
- **前后端开发者无需理解业务数据模型。** 他们各自独立工作在各自的层面。
- **Schema 建模师定义数据结构、关系和函数** — 这是业务逻辑的唯一真相来源。前端基于shema自动渲染，校验，数据联动，后端自动维护表结构，自动处理CRUD和数据推送。
- **没有针对单表的 API 开发。** 系统约 40 个通用 API 基于 Schema 配置动态处理所有 CRUD 操作。
- **业务逻辑层零 Bug。** 由于 Schema 模型是声明式的，运行时是通用的，没有手写的业务代码可以引入 Bug。

### 成果

| 指标 | 传统方式 | Datanode 方式 |
|------|----------|---------------|
| 需要的 API | ~2,000 | ~40 |
| 开发工作量 | ~80–150 人月 | ~9 人月 |
| 新核算标准部署 | 数月 | **1 周（含测试）** |
| 生产环境修复 | 需要重新发版 | **在线配置更改** |
| 前后端协作 | API 契约驱动 | Schema 驱动 |

按传统企业开发模式，这类系统第一阶段通常需要约 80～150 人月 才能完成。即使放到今天，结合 AI 自动生成 CRUD、接口和基础页面，由于跨表关系、动态表单、数据联动等业务复杂度依然需要人工设计与验证，整体工作量仍约 40～70 人月。

而通过 Schema 驱动的数据模型 与 DataNode 第一版，我们将第一阶段实际投入控制在 9 人月（3 人 × 3 个月）。这一投入不仅完成了农业碳汇核算系统第一版，还包括了 DataNode 自身前后端框架的设计与实现，实现了约一个数量级的人力压缩。

第一阶段完成后，每增加一个核算标准约增加 70-80 张表。整个周期——建模、配置、前端适配、测试——**在一周内完成**，无需重新发版。

值得注意的是，DataNode 第一版的设计重点并不是后端，而是前端。

项目中真正消耗开发时间的并非 CRUD，而是复杂的数据关联：单个表单往往需要关联数十甚至上百个数据源，不同字段之间存在级联限制、动态过滤、条件显示等大量联动逻辑。因此，第一版 DataNode 的核心能力几乎全部围绕前端动态表单展开，包括数据源绑定、字段联动、表达式计算以及统一的数据访问模型。

到第二版，随着关联查询需求不断增加，relation 才开始承担更完整的语义描述能力，并在后端参与关联解析，例如支持 displayOnly 等关联查询，使 Schema 中描述的数据关系能够同时驱动前端展示与后端查询，而不再只是 UI 层的配置。

## 第二版：SchemaNode — 替代低代码平台（2025 年中）

### 动机

到 2025 年，系统已在生产环境中稳定运行四年。下一个挑战：**替代商业低代码平台**，构建一个能力更强、更可扩展的基础设施。

这需要远远超出第一版范围的能力：
- **认证与授权** — 在 Schema、App、行、列各级别的细粒度访问控制
- **事件系统** — 数据变更、Schema 变更和自定义事件的发布/订阅
- **工作流引擎** — 基于 DAG 的工作流编排，支持 Fork
- **App Workflow** — 集成到 Schema 模型中的应用工作流定义

### 关键新增

| 系统 | 描述 |
|------|------|
| **Auth** | 基于策略的授权，使用求值函数；支持 `Auths`（通用）、`RowAuths`（行级过滤）、`ColAuths`（列级过滤） |
| **Event** | 基于 Topic 的发布/订阅，支持通配符（`+` 单级、`*`/`#` 多级）；Reactive Extensions 后端；Kafka/RabbitMQ 源支持 |
| **Workflow** | DAG 节点：`WaitEvent`、`Call`、`Interaction`，以及控制流（`Break`、`Exit`、`Goto`、`Delay`、`TimeSchedule`）；Quartz.NET 调度 |
| **微服务集成** | 将现有微服务函数注册为 Schema 函数，实现跨服务工作流编排 |
| **MCP** | Model Context Protocol 支持，AI 代理可读取和理解完整的 Schema 语义模型 |

### 架构演进：Meta/Property 分离

第一版中 Meta 属性和 Property 属性混合在一起。当前端团队需要 `color`、`layout`、`width` 等面向显示的属性时，很明显 **元数据（结构定义）** 和 **属性（行为注解）** 需要分离：

- **Meta**：定义 Schema Kind *是什么* — 其身份和核心结构
- **Property**：定义数据*如何行为* — 约束、显示规则、关系

这种分离使得丰富的前端配置成为可能，而不会污染核心结构定义。

### 发现的设计债务

Meta/Property 分离暴露了一个更深层的问题：**系统的扩展模型与单个 Schema 族紧密耦合。** 添加新类型的 Schema、属性或编译策略需要修改核心代码。架构需要另一个抽象层次。

## 第三版：Core/App 分离 — 三层扩展能力（2026 年 4 月）

### 洞察

第三版的基本洞察：**SchemaNode 不是一个应用平台 — 它是一个构建应用平台的平台。**

这意味着将代码库分为两层：

- **`SchemaNode.Core`**：最小化的、厂商中立的内核。定义了四大支柱架构（Meta + Property + Relation + Function）和 Node Schema 族。不包含任何应用特定代码。**核心代码极少** — 企业不会"被绑定"，因为内核只有1.5k执行代码，而其余代码均是纯申明式，虽然心智门槛有要求，但易读。
- **`SchemaNode.App`**：基于 Core 构建的参考应用层。提供 App/AppField/AppWorkflow、Event、Workflow、Auth 和数据管理。可以直接使用构建应用，例如替代低代码处理业务数据，也可以完全替换或者改写，使用SchemaNode系统只需要保证SchemaNode.Core不被修改即可。

### 三层扩展能力

| 层次 | 受众 | 可以做什么 | 示例 |
|------|------|-----------|------|
| **Core 层** | 平台架构师 | 定义新的 Schema 族 | 新的 Schema Kind + Generator + Runtime Type |
| **架构层** | 解决方案架构师 | 添加新的 Property、CompileContext、Event 类型、Workflow 类型、API 协议 | `QueryFilterCompileContext`、新约束属性、Kafka 事件源 |
| **工程师层** | 开发者与建模师 | 定义新的 Schema 类型、函数、完整应用 | 新的结构体类型、业务函数、带字段和工作流的完整 App |

### 各层可扩展的内容

**在 Core 层**，您可以创建全新的 Schema 族 — 不仅仅是现有 Node Schema 族中的新 Schema，而是拥有自己的 Kind 系统、自己的运行时类型、自己的 Generator 的新族。SchemaNode.App 只是其中一个族。

**在架构层**，您可以：
- 注册任何 Schema Kind 都可消费的新 `Property<T>` 子类
- 实现新的 `CompileContext` 子类，以不同方式解释函数（例如，将验证函数编译为 GraphQL 过滤语法的 `GraphQLCompileContext`）
- 定义新的事件类型和工作流节点类型
- 实现新的 API 协议（JSON-RPC、gRPC 等）用于微服务通信
- 注册新的上下文提供者，注入认证、本地化或业务上下文

**在工程师层**，您可以：
- 定义新的数据类型（结构体、枚举）及其字段和约束
- 将新的原子函数（C# 方法）注册为 Schema 函数
- 定义完整的应用程序，包括字段、工作流和授权策略
- 配置跨应用数据关系和数据推送管道

### 设计原则

1. **最小化核心**：`SchemaNode.Core` 只包含 Schema 定义和解析绝对必要的内容。所有应用特定的内容存在于 `SchemaNode.App` 或第三方包中。
2. **无厂商锁定**：因为 Core 小而精确定义，企业可以用自己的应用层替换 `SchemaNode.App` 而不会丢失 Schema 投资。
3. **渐进披露**：简单用例（定义带字段的结构体）只需最少代码；复杂用例（自定义 CompileContext）可以实现但不强制要求。
4. **语义函数作为通用接口**：函数保持为层之间的桥梁 — Core 中定义的函数可以被不同应用层的不同 CompileContext 以不同方式编译。


## 为什么这段历史重要

SchemaNode 的每个设计决策都有来自真实世界失败或成功的具体起源：

| 设计决策 | 起源 |
|----------|------|
| 语义函数（非图灵完备脚本） | 暖通 Lua 灾难 — 不可分析的脚本不可维护 |
| 唯一真相：一个函数 → 过滤 + 验证 | 碳汇核算 — 无法在 700 张表中维护分离的过滤和验证逻辑 |
| Schema 驱动的零 API 架构 | 碳汇核算 — 3 人无法编写和维护 2,000 个 API |
| Meta/Property 分离 | v2 前端需求 — 结构身份 ≠ 行为注解 |
| Core/App 分离与三层扩展 | v2 设计债务 — 紧密耦合阻碍生态成长 |
| 最小化核心 | 企业需求 — 无厂商锁定；自由替换 App 层 |

SchemaNode 不是元数据理论的学术练习。它是一个**经过实战检验的平台**，诞生于极端真实世界的约束，并通过多年的生产使用不断完善。
