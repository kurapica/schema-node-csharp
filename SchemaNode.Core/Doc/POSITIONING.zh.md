# SchemaNode — 定位与愿景

> SchemaNode 不是一个低代码平台。它是一个**消除所有参与者不确定性的系统**——无论参与者是人类开发者、领域建模师，还是 AI 代理。

---

## 1. 我们真正解决的问题

大多数平台承诺让开发"更快"或"更简单"。SchemaNode 解决的是一个不同的问题：**不依赖任何参与者可靠性的系统可靠性。**

### 不确定性问题

每个软件项目面临四类不确定性：

| 来源 | 表现 | 传统方案 |
|------|------|---------|
| **开发者错误** | 手写业务逻辑中的 Bug | 代码审查、测试、资深监督 |
| **沟通断裂** | 前后端契约不匹配 | API 文档、会议、协调 |
| **平台锁定** | 无法超越厂商路线图演进 | 接受限制或迁移 |
| **AI 幻觉** | 生成的代码看似正确实则错误 | 人工审查每个 AI 输出 |

每种传统方案都增加了成本，并且依赖于**它试图弥补的人类可靠性本身**。

### SchemaNode 的方案

SchemaNode 在系统层面而非参与者层面解决这些问题：

| 来源 | SchemaNode 的方案 | 为什么有效 |
|------|-------------------|-----------|
| 开发者错误 | 声明式 schema，通用运行时 | 无手写业务代码 → 无业务 Bug |
| 沟通断裂 | Schema 作为唯一真相来源 | 前端自动渲染，后端自动 CRUD——无需协商 |
| 平台锁定 | 极简 Core，可替换 App 层 | Core 仅 Meta+Property+Relation+Function；App 只是众多族之一 |
| AI 幻觉 | AI 生成 schema 配置而非代码 | 配置受运行时约束；无法调用未注册的函数 |

统一原则：**不要让参与者更可靠。让系统不需要他们的可靠性。**

## 2. 市场定位：被忽视的象限

企业软件服务了四个市场象限中的三个。有一个仍无人服务：

```
                        低数据复杂度              高数据复杂度
                    ┌─────────────────┬─────────────────────────┐
   高预算           │  SaaS 审批流    │   SAP、定制 ERP          │
   (大企业)         │  (充分服务)     │   (充分服务)             │
   ─────────────────┼─────────────────┼─────────────────────────┤
                    │                 │                         │
   低预算           │  Google Forms   │   ← SchemaNode          │
   (中小企业)       │  Airtable       │   (无人服务)            │
                    │  (充分服务)     │                         │
                    └─────────────────┴─────────────────────────┘
```

右下角——**高数据复杂度 × 低预算**——无人服务。不是因为罕见，而是传统成本结构使其无利可图：开发成本随表数和跨表关系线性增长，而项目预算不会。低代码平台需要昂贵顾问配置复杂数据关联。

但这些场景比比皆是：带参数化 SKU 的五金批发、农业合作社管理、工程造价、检测机构样品跟踪、外贸跟单。每个都有几十到几百张高度关联的表，预算以千计而非十万计。

SchemaNode 的成本结构根本不同：**成本 ≈ Σ(schema 定义)**——运行时是通用的。

### 我们刻意不做的事

- **❌ 审批流**——钉钉、飞书、Teams 已免费提供，无重复价值。
- **❌ 拖拽 UI 构建器**——SchemaNode 从 schema 自动渲染表单，视觉布局次于数据正确性。
- **❌ 企业级权限矩阵**——大企业问题；SchemaNode 的 Auth 功能完备但刻意极简。

## 3. 三层愿景

### 第一层——高复杂度数据管理（今日，已验证）

替代 5000 个 Excel 的混乱。定义数据结构、关系、函数为 schema。前端自动渲染带验证和字段联动的表单。后端自动管理表结构和 CRUD。

**已验证**：4+ 年生产运行。700 张表，3 人，3 个月。新核算标准（约 70 张表）一周内部署。

### 第二层——语义集成（今日可用）

遗留微服务注册为 schema 函数——一行 C#：

```csharp
[Meta<Function>("erp.check_stock", Returns = "int")]
```

RabbitMQ/Kafka 事件成为 schema 事件。工作流编排跨系统交互——这些系统从来不是为了互操作而设计的。AI 代理通过 MCP 读取完整的语义网络。

**已验证**：2 小时迁移替代商业低代码平台，含微服务代理注册和消息队列订阅。

### 第三层——AI 原生的临时应用（未来）

AI 通过 MCP 读取企业语义 → 创建临时 App schema 和工作流 → 执行 → 销毁 → 全链路日志归档。

```
用户："汇总 Q2 各区域客户采购额，标出超过 10 万的客户"
AI：  读取 crm.accounts、erp.orders、erp.order_items 及其关系
      → 创建临时 App "tmp.q2_summary"
      → 执行区域汇总的 push 函数
      → 返回结果，销毁 App，App+输入+输出归档为审计日志
```

与"AI 生成代码"的关键区别：AI 的输出是 **schema 配置**，不是可执行代码。它人类可读、运行时受限（只能调用已注册的函数）、可审计（App 定义 + 执行日志 = 完整记录）、用完即弃——无论背后的参与者是人还是 LLM。

## 4. 设计哲学

### 通过约束而非能力实现可靠性

企业软件的主流方案是能力累积：更多功能、更多权力、更多灵活性。SchemaNode 相反：**系统层面的约束创造可靠性，无论参与者能力如何。**

| 约束 | 可靠性保障 |
|------|-----------|
| 语义函数（非图灵完备） | 静态可分析；无隐藏副作用 |
| CompileContext 系统 | 一个函数定义 → 多种编译目标；无重复逻辑 |
| 声明式 schema，通用运行时 | 无手写业务代码 → 无业务逻辑 Bug |
| 基于 Property 的扩展 | 新能力无需改动 Core；无回归风险 |
| Schema 族作为扩展边界 | 第三方创建新族无需 fork Core |

### "唯一真相"原则

一条业务规则应只存在一次，编译为所有需要的形式：

- `score >= threshold` → 数据录入约束 AND 查询过滤条件 —— 同一个函数，不同 CompileContext
- `SUM(orders.amount)` → 聚合逻辑 AND 缓存失效依赖图 —— 一个 push 函数

这消除了业务系统中最常见的 Bug 来源：**同一规则在不同系统层中的发散实现。**

### 为无法承受错误的团队而建

SchemaNode 不是在架构评审室里设计的。它是由一个无法承受任何错误的 3 人团队设计的——没有时间修 Bug，没有精力协调沟通，没有余地被平台锁定。

结果：团队规模、技能水平、AI 参与度不决定系统可靠性。

---

## 5. SchemaNode 不是什么

- **❌ 不是低代码平台。** 竞争的是复杂数据的成本结构，不是可视化拖拽。
- **❌ 不是审批流工具。** 钉钉、飞书、Teams 已解决。
- **❌ 不是数据库 ORM。** Schema 是产品；数据库是实现细节。
- **❌ 不是 AI agent 框架。** 提供 agent 可读的语义基础；不管理 agent 编排。
- **❌ 不是遗留系统替代方案。** 在旧系统之上叠加语义；迁移可选。
